# evolve — feed what projects learn back into the template

Evolution mode is a user-level, opt-in layer: a separate git repo (`dev-env-evolution`) that every
project on this machine can write to. Hooks append raw signals automatically (blocked commands,
approved confirms, hook errors, ignored wiki nudges, generated skills). This skill turns signals
and ideas into improvement candidates and promotes the good ones into the template.

```
events/<project>/YYYY-MM.jsonl   raw signals, append-only, written by hooks
candidates/<date>-<slug>.md      curated ideas with evidence
platform/                        machine knowledge shared by projects (e.g. GPU host facts)
index.md                         regenerated by review
projects.md                      registered projects
```

**Firewall:** everything in the evolution repo must be generic. No client names, project code,
paths, data, or secrets. Before writing a candidate, rewrite project specifics into general terms
and show it to the user.

## setup — turn evolution mode on (once per machine)
1. `echo $DEV_ENV_EVOLUTION_HOME`: if set and the directory exists, it is already on; just
   register this project (step 4).
2. Ask where (default `~/Projects/dev-env-evolution`) and whether to create a new repo or clone an
   existing remote. Create the skeleton from `references/skeleton.md`, `git init`, first commit.
   Offer `gh repo create <name> --private --source . --push` (ask first: it is outward-facing).
3. The switch lives in `~/.claude/settings.json`, which is a guard file (P0): you cannot write it.
   Give the user this command to run themselves with `!`:
   `! python3 .claude/skills/evolve/scripts/apply_user_settings.py <path>`
   It sets `env.DEV_ENV_EVOLUTION_HOME` and adds the path to `permissions.additionalDirectories`.
   It takes effect in new sessions.
4. Register the project in `projects.md` (slug, date). Ask: is this a client or employer repo?
   If yes, the user should add `"DEV_ENV_EVOLUTION": "0"` under `env` in
   `.claude/settings.local.json` (also a guard file; give them the exact JSON).

## note — capture an idea now
Write `candidates/<YYYY-MM-DD>-<slug>.md` (template in `references/skeleton.md`) with a concrete
situation as evidence. An idea without a situation is not a candidate yet.

## review — turn events into candidates
1. `python3 .claude/skills/evolve/scripts/evo_review.py "$DEV_ENV_EVOLUTION_HOME"` prints clusters
   (kind + rule/hook/skill, event count, projects, first/last seen) and open candidates.
2. A cluster becomes a candidate when it has ≥ 2 events or ≥ 2 projects. Update an existing
   candidate's evidence instead of duplicating it.
3. Typical readings: many `p2_approved` or repeated `p1_blocked` for one rule → rule too strict
   (hook-false-positive) · `hook_error` → hook bug · many `wiki_nudge_declined` → nudge too eager ·
   `wiki_check_failed` → schema or skill unclear · `skill_generated generic=yes` → new-skill.
4. Close candidates with no new evidence for 90 days (`status: rejected`, reason "stale").
5. Regenerate `index.md` (table: id · kind · target · status · evidence count) and commit the
   evolution repo (`git -C "$DEV_ENV_EVOLUTION_HOME" add -A && git commit -m "review <date>"`).

## promote — move an accepted candidate into the template
Needs the template checkout (ask for the path; default `~/Projects/agentic_dev_env`).
1. Show the candidate; the user decides accept / reject.
2. Accept: in the template repo write an ADR in its `eng-wiki/decisions/` (cite the candidate),
   make the change under `template/`, run the template's tests, and commit on a branch.
3. Mark the candidate `status: promoted` with the template commit. Projects pick the change up
   with `copier update`.

## seed — import learnings from existing repos (one-time)
For each repo given: read its wiki learnings/insights. Sort each into: dev-environment lesson →
candidate (`kind: improvement` or `friction`, evidence = the original page path) · machine/
platform fact → `platform/<topic>.md` · library gotcha → leave it (stack-docs picks it up per
project) · project-specific → leave it. Show the list before writing.
